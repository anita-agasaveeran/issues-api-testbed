# issues-api-testbed

A FastAPI service that wraps the GitHub REST API for Issues on a single repository,
plus signed-webhook ingestion for `issues` and `issue_comment` events.

## What it does

| Route | Purpose |
| --- | --- |
| `POST /issues` | Create an issue → `201` + `Location` |
| `GET /issues` | List issues, with pagination and ETag caching |
| `GET /issues/{number}` | Fetch one issue |
| `PATCH /issues/{number}` | Rename, edit, close, or reopen |
| `POST /issues/{number}/comments` | Add a comment → `201` |
| `GET /issues/{number}/comments` | List an issue's comments |
| `POST /webhook` | Verify and record a signed GitHub delivery → `204` |
| `GET /events` | The last N processed deliveries, for debugging |
| `GET /healthz` | Liveness; never contacts GitHub |

## Quick start (no Docker)

Requires Python 3.11 or newer.

```bash
make install
```

```bash
cp .env.example .env
```

Fill in `GITHUB_TOKEN` and `WEBHOOK_SECRET` (see [scopes](#github-token-scopes)). Generate the secret with:

```bash
python3 -c "import secrets; print(secrets.token_hex(32))"
```

Then run it:

```bash
make run
```

Check it came up:

```bash
curl -s http://localhost:8000/healthz
```

```json
{"status":"ok","version":"0.1.0","repo":"anita-agasaveeran/issues-api-testbed"}
```

Interactive docs are at <http://localhost:8000/docs>. Note that page is generated by
FastAPI from the code; [`openapi.yaml`](openapi.yaml) is the authoritative contract,
and a test fails if the two drift apart.

## Environment variables

All configuration comes from the environment. Nothing is hard-coded, and `.env` is
git-ignored — commit only `.env.example`.

| Variable | Required | Example | Purpose |
| --- | --- | --- | --- |
| `GITHUB_TOKEN` | yes | `github_pat_...` | Fine-grained PAT used for all GitHub API calls |
| `GITHUB_OWNER` | yes | `anita-agasaveeran` | Owner of the target repository |
| `GITHUB_REPO` | yes | `issues-api-testbed` | Target repository name |
| `WEBHOOK_SECRET` | yes | `a-long-random-string` | Shared secret for `X-Hub-Signature-256` HMAC verification |
| `PORT` | no (default `8000`) | `8000` | Port the service listens on |
| `DATABASE_URL` | no (default `sqlite:///./events.db`) | `sqlite:///./events.db` | Local store for webhook deliveries |
| `LOG_LEVEL` | no (default `INFO`) | `DEBUG` | Structured-log verbosity |
| `EVENTS_MAX_LIMIT` | no (default `200`) | `200` | Hard cap on `GET /events?limit=` |
| `CACHE_ENABLED` | no (default `true`) | `false` | Toggle the ETag response cache |
| `CACHE_MAX_ENTRIES` | no (default `128`) | `128` | LRU size of that cache |

Secrets are held as pydantic `SecretStr`, so an accidental log or `repr` of the
settings object prints `**********` rather than the value.

## GitHub token scopes

Use a **fine-grained personal access token** (Settings → Developer settings →
Personal access tokens → Fine-grained tokens) scoped to **only this repository**.
This is the least privilege that satisfies every route in the service.

| Permission | Access | Why it is needed |
| --- | --- | --- |
| **Issues** | Read and write | `POST /issues` (create), `GET /issues` and `GET /issues/{number}` (read), `PATCH /issues/{number}` (edit title/body, close/reopen), `POST /issues/{number}/comments` (create comment) |
| **Metadata** | Read-only | Mandatory for every fine-grained token; required to resolve the repository itself |

Notes:

- **Repository access:** select *Only select repositories* → `issues-api-testbed`.
  Do not grant organization- or account-wide access.
- **Not required:** `Contents`, `Pull requests`, `Administration`, `Actions`, or any
  account permission. The service never reads code, never touches pull requests, and
  never changes repository settings. Webhook creation is done once by hand in the UI,
  so the token does not need `Webhooks: Read and write` either.
- **Classic token equivalent (only if fine-grained tokens are unavailable):** the
  `repo` scope. This is deliberately broader than the service needs — it grants full
  read/write to code and settings on every repository you can access — so prefer the
  fine-grained token above.
- **Expiration:** set a short expiry (e.g. 30 days). The service surfaces an expired
  or revoked token as a `401` with a clear message rather than a generic `500`.
- The token is read from `GITHUB_TOKEN` at startup and is never logged. Webhook
  signatures and `WEBHOOK_SECRET` are likewise excluded from all log output.

## API reference

Every example below is shown twice: `curl` first, then the [HTTPie](https://httpie.io)
equivalent. `BASE` is `http://localhost:8000`.

### Create an issue

```bash
curl -i -X POST http://localhost:8000/issues -H 'Content-Type: application/json' -d '{"title":"Checkout button is dead","body":"Nothing happens on Safari 17.","labels":["bug"]}'
```

```bash
http POST :8000/issues title="Checkout button is dead" body="Nothing happens on Safari 17." labels:='["bug"]'
```

```http
HTTP/1.1 201 Created
Location: /issues/42
X-Request-ID: b00d0e4c-46da-4bc3-8ec6-66d22f349b45
```

```json
{
  "number": 42,
  "title": "Checkout button is dead",
  "body": "Nothing happens on Safari 17.",
  "state": "open",
  "labels": ["bug"],
  "html_url": "https://github.com/anita-agasaveeran/issues-api-testbed/issues/42",
  "user": "anita-agasaveeran",
  "comments": 0,
  "created_at": "2026-09-01T10:00:00Z",
  "updated_at": "2026-09-01T10:00:00Z",
  "closed_at": null
}
```

### List issues

```bash
curl -i 'http://localhost:8000/issues?state=open&labels=bug&page=1&per_page=10'
```

```bash
http GET :8000/issues state==open labels==bug page==1 per_page==10
```

Response headers carry pagination and cache information:

```http
HTTP/1.1 200 OK
Link: </issues?page=2&per_page=10>; rel="next", </issues?page=5&per_page=10>; rel="last"
ETag: W/"6c1b2f0e9a"
X-Page: 1
X-Per-Page: 10
X-Cache: MISS
```

Repeat the request and `X-Cache` becomes `HIT`: the service replayed the cached ETag
upstream, GitHub answered `304`, and the response cost no rate-limit quota.

You can also send your own validator, which takes precedence and yields a real `304`:

```bash
curl -i 'http://localhost:8000/issues' -H 'If-None-Match: W/"6c1b2f0e9a"'
```

### Get one issue

```bash
curl -s http://localhost:8000/issues/42
```

```bash
http GET :8000/issues/42
```

### Update, close, and reopen

```bash
curl -s -X PATCH http://localhost:8000/issues/42 -H 'Content-Type: application/json' -d '{"title":"Checkout button unresponsive on Safari"}'
```

```bash
http PATCH :8000/issues/42 state=closed
```

```bash
http PATCH :8000/issues/42 state=open
```

At least one of `title`, `body`, or `state` must be present; `{}` is a `400`.

### Comment on an issue

```bash
curl -i -X POST http://localhost:8000/issues/42/comments -H 'Content-Type: application/json' -d '{"body":"Reproduced on Safari 17."}'
```

```bash
http POST :8000/issues/42/comments body="Reproduced on Safari 17."
```

### List comments

```bash
curl -s 'http://localhost:8000/issues/42/comments?per_page=50'
```

```bash
http GET :8000/issues/42/comments per_page==50
```

### Inspect processed webhook deliveries

```bash
curl -s 'http://localhost:8000/events?limit=20' | python3 -m json.tool
```

```bash
http GET :8000/events limit==20
```

### Error shape

Every failure uses one envelope, so a client parses a single shape:

```json
{
  "error": {
    "code": "not_found",
    "message": "Issue #999 does not exist in this repository.",
    "details": { "issue_number": 999 },
    "request_id": "7830098e-2558-4aae-abb2-08277b81ec98"
  }
}
```

`request_id` matches the `X-Request-ID` response header and appears on every log
line for that request. See [DESIGN.md](DESIGN.md) for the full mapping table.

## Webhook setup

The service must be reachable from GitHub, which means a public tunnel during
development. Use three terminals.

**1. Run the service** (no `--reload`: the reloader's child process would hold a
second event store, and deliveries would land in whichever one GitHub reached):

```bash
make serve
```

**2. Open a tunnel** and copy the printed `https://….trycloudflare.com` URL:

```bash
make tunnel
```

Install it first if needed with `brew install cloudflared`. `ngrok http 8000` and
`smee` work equally well.

**3. Add the webhook** — repo → Settings → Webhooks → Add webhook:

| Field | Value |
| --- | --- |
| Payload URL | `https://<your-tunnel>/webhook` |
| Content type | `application/json` |
| Secret | the same value as `WEBHOOK_SECRET` in `.env` |
| Events | "Let me select individual events" → **Issues** and **Issue comments** only |

GitHub sends a `ping` on save. Confirm it arrived:

```bash
curl -s http://localhost:8000/events | python3 -m json.tool
```

A `401` in GitHub's *Recent Deliveries* tab means the secret does not match.

### Redelivering an event

In the webhook's **Recent Deliveries** tab, open a delivery and press **Redeliver**.
GitHub logs every attempt there, so a second row always appears in *its* list — that
is GitHub's bookkeeping, not a duplicate in this service. To check what this service
recorded, compare `GET /events` before and after: the row count must not change.

For a self-contained proof that does not depend on GitHub's behaviour:

```bash
make replay
```

[`scripts/replay_webhook.py`](scripts/replay_webhook.py) signs one payload, posts it
three times under a single delivery id, and reports how many rows `/events` holds:

```
  attempt 1: HTTP 204
  attempt 2: HTTP 204
  attempt 3: HTTP 204

deliveries sent            : 3
rows stored for that id    : 1

PASS - repeated deliveries were deduplicated.
```

## Testing

```bash
make test
```

Runs the unit suite with coverage and fails below 80%. No credentials needed —
integration tests detect their absence and skip themselves.

```bash
make lint
```

Ruff (lint + format check) and mypy in strict mode.

### Integration tests against real GitHub

With `.env` populated:

```bash
make test-integration
```

These create real issues in the configured repository and close them afterwards.
GitHub's API cannot delete an issue, so closed issues are the expected residue.

### Webhook end-to-end

With `make serve`, `make tunnel`, and the webhook configured:

```bash
make test-webhook
```

Creates an issue, then polls `GET /events` until the signed delivery for it appears.

### What is covered

| Area | Where |
| --- | --- |
| Route validation, HTTP semantics | `tests/unit/test_routes_issues.py` |
| Signature verification, tampering | `tests/unit/test_webhooks.py` |
| Error mapping for every GitHub status | `tests/unit/test_github_client.py` |
| `Link` parsing and rewriting | `tests/unit/test_pagination.py` |
| Idempotent delivery storage | `tests/unit/test_store.py` |
| ETag caching | `tests/unit/test_cache.py` |
| Contract validity and drift | `tests/unit/test_openapi_contract.py` |
| Real GitHub round trips | `tests/integration/` |

Rate-limit and 5xx paths are covered with mocked transports (`respx`) rather than by
provoking a real rate limit.

## Project layout

```
app/
  main.py            # app factory, lifespan, /healthz
  config.py          # env-sourced settings; secrets as SecretStr
  github_client.py   # GitHub calls + the single error-mapping table
  routers/
    issues.py        # issue and comment routes
    webhooks.py      # POST /webhook, GET /events
  webhooks.py        # HMAC verification, payload summarising
  store.py           # SQLite delivery store, keyed for idempotency
  cache.py           # LRU ETag cache
  pagination.py      # Link header parse/rewrite
  errors.py          # error hierarchy and handlers
  logging.py         # structlog JSON + request-id middleware
tests/
  unit/              # fully mocked; no network
  integration/       # real GitHub; skipped without credentials
  fixtures/          # captured GitHub payloads
scripts/
  replay_webhook.py  # idempotency proof
deploy/Caddyfile     # reverse proxy config for compose
```
